# CLI 开发工作流：从 SOW 到 SPEC 到可运行 Demo

## 目标

学生能用 Claude Code / Codex 的 CLI 工作流，把 SOW 转成一个每一步有截图、有测试留痕的企业 Agent Demo。

## 讲授

**工具选择。** 第一梯队是 Claude Code 和 Codex，其次 Cursor；再往后的（微软 Copilot 等）基本不用看。Lyon 自述从 2025 年 6 月开始用 Claude Code，已稳定使用几千个小时，强烈推荐；Codex 新版本表现越来越好，可用桌面端工具，也支持沙箱和批量化任务。在本地用 CLI 做的好处：有完整代码库、有系统命令、能进内网、能做 CI 批量编排，上下文管理和 memory 管理也更好。

**起手式。** 新建项目后，先写好 AGENTS.md / CLAUDE.md——说清楚我们要做什么项目；再把 SOW 和客户的整个需求文件输进去，让工具转成 SPEC（规范化的项目与 Demo 描述）；然后用**小步指令**一步步做 Demo，每一步都让它截图和跑测试。

**用最好的模型。** 这是有商业逻辑的选择：企业客户的耐心有限，信任建立很不容易，必须用最好的模型、最好的效果去打动客户。招投标过程中，Demo 做到技术标第一名对赢得信任至关重要。做 toB 大标，千万不要吝啬模型。

**CLI 参与企业开发的动作清单。**

1. 读懂陌生代码库——客户三年甚至十几年的老项目，可能是网管写的古老 CMS，先读懂再动手；
2. 接内部系统——通过 OpenAPI、Webhook 接客户的客户端和 mock 层；
3. 跑客户内网或沙箱——除很小的客户可以直接进生产，中型客户一般都要求你的代码跑他的沙箱、部署到他的服务器；
4. 跑无人值守的 Agent 自动化任务；
5. 客户隐私数据的多模态提取——隐私数据要么布到内网，要么用端侧模型先脱敏，脱敏后的非隐私数据再调公网大模型 API。

一个澄清（来自答疑）：课程里讲的用 Claude Code / Codex，是在**给客户搭 Demo 的过程中**用，而不是把这些工具直接接入客户的系统。

**一个人能带多少个 agent。** multi agent 的并发上限，在 toB 场景一般是**三到五个**——因为 toB 项目复杂，需要花大量精力理解客户业务；纯 toC 项目或单一功能研发可以带得更多。工程纪律上要求上下文延续：SOW → SPEC → 小步 → 留痕。

**把客户现场变成 Demo 工厂。** 把客户的派单记录、需求转写、旧系统截图都放进 CLI 工具，模拟客户场景做出可重复的 Demo。课程举的例子：制造业售后工单的超时智能派单——从旧系统现状出发写 SOW、转 SPEC，做出超时看板和派单建议，再跑测试、出 Demo。

## 常见误区

- "Demo 阶段就把工具接进客户生产系统"——搭 Demo 归搭 Demo；中型客户要求先跑沙箱、部署到他的服务器；
- "省一点模型钱"——做 toB 大标时模型费用是最不该省的钱，客户耐心有限；
- "隐私数据直接调公网 API"——先内网部署或端侧脱敏，非隐私数据才能出公网；
- "一把梭大需求"——要小步指令、每步截图跑测试、全程留痕，否则 vibe coding 出的代码出 bug 没法修。

## 实验

1. 新建一个项目文件夹，写好 CLAUDE.md（项目目标）和一份模拟客户需求的 SOW 文件，让 CLI 工具把它转成 SPEC，保留转换产物；
2. 用小步指令实现 Demo 的一条核心路径，每一步要求工具截图或跑测试，全部留痕到证据目录；
3. 同时开几个 agent 会话干活，记录从第几个开始质量明显下降，找到你自己的并发上限（对照课程给的 3–5 个）。

## 证据

项目目录里真实存在：CLAUDE.md、SOW→SPEC 的转换产物、可运行的 Demo、每一步的测试与截图留痕；学生能说出"用最好的模型"背后的商业逻辑。
