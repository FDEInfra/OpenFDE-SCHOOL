# 为什么是 CLI 而不是 MCP

## 目标

学生能讲清企业内部系统接入从 MCP 转向 CLI 的原因，并能按场景在 API、CLI、MCP 三者之间做出选型并说出理由。

## 讲授

**一个标志性信号。** 2026 年 3 月，推特上有资讯称 Perplexity 的创始人兼 CTO 在 ASK 大会（音译存疑）上表态：Perplexity 内部正在从 MCP 转向 API 和 CLI。讲师吴明（音译存疑）当时为此发过公众号文章，部分同学已经 get 到，部分同学没有在意。

**MCP 的缺点（讲师逐条列举）。**

- **上下文膨胀**：MCP 装完后，智能体启动时就会拉取全部工具的 schema，特别占上下文；可能一整天都没用到这些平台，光是平台元信息就占掉大量 token；挑着关、来回开关都很麻烦；
- **多了一层**：没有必要就不要增加实体——多一层就多一份耗时、多一个出错点，出错时还不知道是 MCP 服务的问题还是下游接口的问题；
- **语义不统一**：显示已连接，底层实际可能不可用；
- **安全问题**：容易造成注入、越权；
- **审计复杂**；
- **固定重复的场景用 MCP 太重**，不如 CLI；
- **MCP 要起一个服务**，而 CLI 或直接 Python 调 API 只是一个脚本。

**大厂的演进路径。** 2026 年初，大厂把很多主要平台做了 MCP 化：运营同学用 Claude Code、Codex、Qoder 装上数据平台的 MCP，自己说清口径就能拉数、做报表，不再找开发。到 2026 年中，很多平台开始 CLI 化——MCP 多一层、不稳定、还要起服务；Java 同学做 MCP 更痛苦，CLI 写个脚本就能轻松装上、稳定调用。大厂内部平台 CLI 化之后，通过 Skill 挂给智能体，按需加载，上下文清爽。

**这不是闭门造车。** 主流平台已经官方提供了 CLI：钉钉开放七大能力；企业微信的文档、表格、消息、待办、会议都可以通过 CLI 打通；飞书也提供了 CLI；瑞幸咖啡同时提供 MCP、CLI 和 Skill 三件套（兼容不同偏好的用户）。注意：它们多用 Node 技术栈，这是后面选型课的伏笔。

**企业数字化的黄金公式。** 系统 CLI 化（让智能体打通内部系统）+ 流程 Skill 化（AI 掌握重复的、枯燥的最佳实践）+ 员工 Agent 化（不同岗位定义成不同 agent）。人主要负责：干活之前的澄清和核对、干活之后的检查把关、智能体搞不定的异常节点。CLI 是其中重要一环。

**CLI 与 HTTP API 的关系。** 人在命令行执行 CLI 时，CLI 做参数解析（区分命令和参数）、读配置环境、构造并发起 HTTP 请求；服务端鉴权、处理、读写数据；CLI 拿到结果后在终端展示。区别在于：CLI 运行在本地（也可能在服务器本地），HTTP 接口运行在服务提供方的服务器上；CLI 是"命令+参数"，HTTP 接口是"方法+URL+header+body"；CLI 不只调 HTTP，也可以直接读写本地文件。HTTP 提供服务，CLI 是使用这个服务的一个入口。

**嘉宾若琪（音译存疑，阿里云百炼 CLI 技术负责人）的口径。** MCP 可以理解为"给 Agent 用的 API"；API 是传统系统的接口；CLI 是一个完整的产品，背后包了很多 API——简单理解，CLI 包含了 MCP、API 等能力。为什么做 CLI 而不是网页控制台：未来的软件本来应该是 AI native 的，过去的软件是为人点界面设计的，Agent 不需要看懂界面、点按钮，它需要的是一个结构化的能力入口，能直接调用并拿到稳定的结果。对照实验：Codex 的 Computer Use 能理解电脑桌面并代为操作，但非常消耗 token、速度更慢，降低了使用 Agent 的效率。

**选型规则（吴明总结，二者非你死我活）。**

- MCP 适合长尾功能、动态扩展：服务端加了新功能，智能体侧不用任何改动就能感知；MCP 的市场生态也做得不错；
- 高频、强 SLA、稳定性要求高、相对固定的场景：接口少，直接 Python 脚本调 API；接口多且稳定，封装成 CLI，再通过 Skill 让智能体感知。

## 常见误区

- "MCP 和 CLI 是你死我活"——不是替代关系，按场景选型；
- "MCP 装得越多越强"——装得多意味着启动即占用大量上下文 token，可能一整天都用不上；
- "CLI 就是给人敲命令的黑窗口"——CLI 正在从给人用、给 Shell 脚本用，转向给智能体用；
- "CLI 跳过了大模型的编解码所以更便宜"——若琪澄清：CLI 的本质是把服务打包成 agent 能直接理解、直接调用的东西，降低的是 agent 做事时的理解成本；
- 认为 CLI 化是大厂跟风——钉钉、企业微信、飞书、瑞幸都已官方提供，是行业现状。

## 实验

1. 选一个你身边真实存在的内部系统或 SaaS（报销、审批、数据平台均可），列出它的接口数量、调用频率、稳定性要求，写下你选 API / CLI / MCP 中的哪一个，各用一句话写理由；
2. 任选钉钉、飞书、企业微信的官方 CLI 之一，按官方文档装上（注意它们多为 Node 栈、npx 一键安装），执行一次 `-h` 和一次真实查询，把输出贴进笔记；
3. 向 Agent 提问"Perplexity 为什么从 MCP 转向 CLI"，核对其回答与本课列出缺点的重合度，把 Agent 漏掉的缺点补上。

## 证据

学生能不看笔记说出：Perplexity 转向信号的内容；MCP 的至少四个缺点（上下文膨胀、多一层、要起服务、安全/审计）;"黄金公式"的三个组成部分；以及"接口少用 Python 调 API、接口多用 CLI+Skill、长尾动态用 MCP"的选型规则。
