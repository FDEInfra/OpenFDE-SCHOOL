# API、CLI 与 MCP：按任务选择接入方式

## 目标

画清三者的关系，为一条具体业务链路作出有依据的选择。

## 讲授

API 是程序访问能力的接口；CLI 把参数、配置、认证与输出组织为命令；MCP 则提供 Agent 与工具服务之间的协议。CLI 可以调用 HTTP API，也可以操作本地文件；MCP 服务也可以调用同一个 API。它们并不是互斥的替代品。

课程提出“系统 CLI 化、流程 Skill 化、员工 Agent 化”的组合，强调固定业务任务适合用清晰命令与流程封装。这里的价值在于任务表达、可测试性和可恢复性，不是保证所有员工都由 Agent 替代。

讲师讨论过工具描述占上下文的成本。应把它理解为某些部署方式的负担；[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)定义了工具发现与调用，客户端怎样加载、缓存或筛选工具，还取决于实现。不能断言所有 MCP 都一次常驻全部工具，或 CLI 天然更安全。

报销练习使用 Python CLI 调用本机 HTTP API，适合查看命令、状态码与审计。若团队已有受治理的 MCP 接入，也可沿用它。权限、安全与业务校验最终必须在可信执行层落实。

## 实验

在 `work/evidence/04-selection.md` 画“使用者/Agent→入口→服务端→数据”的图，分别填上直接 API、CLI、MCP 三个入口。比较认证、发现、部署、日志、失败定位五项，选择当前最小可行的一种。

读取 `references/lab-guide.md` 并执行一次 `--help`。指出 `list` 如何走到 HTTP 请求，而离线 `eval` 为什么不用启动服务。

## 验收

选择理由针对自己的任务和环境；图里保留服务端鉴权与业务校验，不能只写“CLI token 少所以更好”。
