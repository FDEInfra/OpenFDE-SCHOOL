# 翻车案例与评审标准：漏检 15 单重复发票的教训

## 目标

学生掌握评委悟鸣从全部作业中提炼的评审标准，并通过乔瑞奇的三次翻车理解"评测是主控回路"这条最值钱的心得。

## 讲授

### 乔瑞奇：一个一线从业者的翻车复盘

乔瑞奇做医疗信息化、多年在项目一线，自己也常被报销折磨，所以一眼相中这个开放 API 的 ERP 题目。他拿到题目先看评分标准，并提醒：真实要落地的项目，**业务人员能不能上手，可能比准确率还重要**。

**业务难点**：会计审一张差旅报销单，要看差旅标准、城市档次、整个审批流程记录，有时还要翻纸质影像数据确认最初的真实情况——审一单要在六个地方来回查阅。方案是用规则加 AI 把六处都核对一遍，给财务一个可直接做下一步判断的建议；数据从 ERP 开放平台拉取，本地引擎跑固定规则，最终给三条建议。**300 单批量预审约一分多钟**，效率提升明显。

**三次翻车，一次比一次值钱：**

1. **明显超标的差旅单，驳回还是放行？** 他第一次直接判了驳回，翻评审记录才发现这是领导事先特批的单子——**单据上完全看不出来**。这是实际业务必须考虑的问题。
2. **评测脚本与提交脚本配置不一致**，导致 15 单重复发票被漏检；还有格式校验通过、数字看着正常，回头看代码才发现不对的情况。
3. **以为程序有问题，其实是数据有问题**：ERP 里录的是简称，发票上写的是全称——这种问题只有真实业务数据才能暴露。

**他提炼的四条心得：**

1. MVP 不是最小的功能，是最小的闭环——先跑通整个流程，再决定丰满哪里；
2. 一开始就把验收标准确立下来；
3. 需要确定性的规则优先交给代码处理，不是所有事都交给 AI；
4. 评测相当于主控回路：没有评测，路线偏差只会越来越偏；评测要在一开始做好、贯穿全程，而不是作为最后的验收。

以及一条收尾判断：AI 给的建议，人需要最终终决；项目虽在 AI 辅助下开发，最终质量把控由他自己完成。

### 悟鸣的评审观察：什么样的作业被认为好

悟鸣不点名地给了整体评价：各有千秋，大家对 FDE 流程的理解普遍比较完整，有同学从最前面的沟通到架构、测试，文档特别全面，配图也很专业。但他花时间讲的是问题面：

- **FDE 与智能体工程师技术上区别不大**，但 FDE 要求更高——AI 水平要高，业务理解也要好；多数同学两头都不够深。
- **不要低估 AI 的难度。** 搞个 Demo 很快感觉很好，就以为上线这么简单；企业里一个低级 bug，客户就会觉得你不专业，以后很难合作。
- **用户思维优先。** 评委不可能关注你材料的每个点：要看打分标准是什么、你的亮点是什么，把亮点突出出来。他印象最深的是一位做了演示视频的同学——评委不一定愿意跑你的系统，视频或文档能把评委关注的点清楚表达出来。面向客户同理：客户最关心的是业务指标，不是你性能优化了多少。
- **测试要被重视。** 单元测试、集成测试、端到端测试、留痕与测试报告，尤其非技术背景同学更不能省。
- **专业细节决定可信度**：用 SVG 画的乱线架构图显得业余；按钮与文字重叠、红色消息框点了没反应这类瑕疵很扎眼；界面上不要出现"POST /xxx"这类技术术语，要屏蔽掉；有同学把 `.env` 里的 key 提交了上去；文档版本管理混乱——代码改了文档不回去更新，新旧文档冲突；多系统之间要考虑丝滑跳转，而不是甩给用户一个文档让他自己开链接。
- **Demo 数据量小会掩盖问题。** 大企业里也一样：Demo 一汇报很开心，真做各种坑——可能是 AI 技术的坑，可能是你不懂业务的坑，甚至你都不知道客户真正想要什么。
- **形态判断**：大多数作品是"网页里嵌一个 AI 功能"，他认为这可能已经落后——大厂里各种系统通过 CLI 或 MCP，让智能体在 Codex、WorkBuddy、Qoder 里全自动操作；未来网页上活的智能体，生命周期可能不如这些形态长。
- **一句话定义**：FDE 是用最适合的技术解决用户最核心的问题；如果你对 CLI、Skill、知识库、智能体、Memory 都不专业，就很难选出合适的技术，也就不要低估做 FDE 的难度。沟通的吞吐量同样不要低估。

### 加餐：Skill 的硬指标与优秀 Skill 点评

- 弗朗西同学的 Skill 非常结构化、专业；观猹员二六三六的 Skill 文档把输入、输出、中间处理捋得很清楚，还考虑到中间产物的精细存储，甚至追问"既然限定了权限，为什么登录还要人来登"——关键环节留人确认没问题，但不等于所有节点都要人介入。
- **Skill 长度**：name 和 description 有限制，description 别太长——有些智能体直接截取前约 126 个字符，你自以为写得好的部分可能被截掉。
- **SKILL.md 别太长**：建议不超过 500 行左右；太长就拆成多个子文件放进 reference，在 SKILL.md 里建索引、写明什么情况加载哪些文件。上千行的 Skill 你自己维护都找不到地方改。
- **没有绝对上限但不代表能力好**：文件夹里放几十万字没问题，靠渐进式加载；但超过底层大模型上限就不行，而且上下文超过 50%–60% 后模型能力就开始下降。
- **多个 Skill 协作**：用自然语言衔接即可，聪明的智能体知道怎么串（他自己用四个 Skill 做"下载视频→转文本→术语对照→回流知识库"）；嫌每次打字麻烦就再封一层 Skill 驱动底层四个，用 Claude Code 的话还可以定义成 commands；复杂端到端流程参考 Superpowers，把每个 Skill 的中间产物定义清楚，在 AGENTS.md 里交代衔接关系。

### 评审标准（从评委反馈中提炼）

1. **明确"不做什么"**：划清 Agent 与人的边界，不做自动审批付款、不对疑似风险擅自判定、不替 AI 做猜测；最终决策由人确认。
2. **评测是主控回路而非最后验收**：测试集覆盖正常、边界与失败注入；评测脚本与交付脚本配置必须一致；用真实业务数据验证，Demo 小数据会掩盖问题。
3. **用户思维优先于技术炫耀**：对照打分标准突出亮点，用视频或文档让评委和客户快速抓住重点；客户最关心业务指标而非技术架构。
4. **专业细节决定可信度**：架构图别潦草、界面别露出 POST/GET、别把 `.env` 的 key 提交进仓库、文档与代码版本要同步。
5. **解决真问题而非"加个 AI 功能"**：痛点不是你觉得的、甚至不是客户嘴上说的；执行前的对焦与执行后的验收，比执行本身更关键。

## 常见误区

- "评测是交付前最后一道手续"——它是贯穿全程的纠偏回路；
- "配置不一致是小问题"——它直接漏掉 15 单重复发票；
- "Demo 跑通就能接 FDE 单"——评委警告：客户对低级 bug 的容忍度极低；
- "Skill 写得越全越好"——description 会被截断，SKILL.md 超 500 行就该拆。

## 实验

1. 用五条评审标准给自己的大作业逐项打分（1–5 分），最低分那一项写出改进动作；
2. 复刻"配置不一致"自查：核对你的评测脚本与交付脚本的配置是否逐行一致；
3. 检查你的 Skill：description 字符数、SKILL.md 行数，超标的当场拆。

## 证据

学生能完整复述 15 单漏检事故的因果链，并用自己的项目实例逐条对照五条评审标准做一遍自查。
