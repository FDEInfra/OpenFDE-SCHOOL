# Demo 案例：启恒精密 AI 财务提效 POC 两例（朱军胜、姜超，挑战赛道）

## 目标

学生通过同题不同解的两个挑战赛道项目，看清财务提效类 POC 的共性骨架（数据安全、规则+AI 双通道、人工兜底、写回企业系统）与各自的取舍。

## 讲授

挑战赛道题目为"启恒精密 AI 财务提效 POC"，五个上麦 Demo 里有三个选了它。本课讲其中两个，第三位作者乔瑞奇的翻车复盘见下一课。

### 朱军胜：M2/M3/M4 三模块的完整改造

作者自述是 27 届在校生，一边学 FDE 一边寻找求职机会。他先从体验 ERP 出发找不合适的地方——比如点进单据看不到票据图片，于是在 M2 合规审核里把票据图片与字段同列展示。

- **M2 合规审核**：使用 PaddleOCR 本地识别，保证票据这类敏感信息不出域；票据图片与系统录入字段比对（以票据图片为准），不一致标记为 flag 或 reject。审核走双通道：一条是把财务手册和访谈记录整理的规则硬编码成硬性匹配（如住宿超标），一条是 AI 知识库审核；两边都判存疑才输出 flag 或拒绝。尽管有评审结论，仍保留人工复核环节——可以输入与评判不同的结果（通过/存疑/驳回）并附复核意见，最终通过 ERP 写回提交审核决定。
- **M3 异常检测**：对全量**两万多张发票**做审核；重复发票做数据字段硬匹配（有的重复发票没有票据，是前系统票据未迁移所致，此时以字段为准）；另一条规则线是税率异常；同样结合 AI 知识库复核。
- **M4 对账**：基于应收台账与发票台账。自动匹配先看金额一致；一笔多票可拆分的做智能化识别匹配；还有来自业务访谈的洞察——事前事后手续费由甲方或乙方承担会造成小额差值，低于阈值的也要匹配。实在无法匹配、账户名不符的，留待人工认领；业务人员自己维护的客户多账户户头表，后续可导入支持人工匹配。
- **工程取舍**：OCR 引擎一开始用千问，考虑数据安全后切换到本地 OCR；M2/M3 的模型调用封装成了 Skill。远期方向包括扩充财务知识库与别名表、增加高级别领导特别豁免、本地化私有部署、把财务规则做成外部可配置以便业务人员自行操作。

### 姜超：证据链复核视角的轻量改造

作者做通信互联网测试与工程项目管理，AI 接触不算多。选题动机很直接：工程项目管理里也有大量材料审批，与财务审批一样存在大量证据链的复核与反复核对。他按第一课的方法先挖真需求：真正耗时的不是点"审批/退回"，而是在一堆资料里反复找证据、核对口径是否统一。

- **交付形态**：用 Docker 部署，直接改造 ERP 原始界面——原始界面没有 AI 审批结论，改造后每条单据能看到 AI 审批结论（通过/未通过）。
- **流程**：证据聚合（ERP 平台提供的默认 API）→ 读取报销单 → 通过聚合接口提取发票与标准相关信息 → 本地 OCR 加规则交叉验证 → 生成审核建议 → 通过 API 写回平台。他把所有资料梳理后封装成对应的 Skill，交叉验证时按规则逐步进行。
- **工程细节**：平台限流，每秒只能请求十次，耗时必须计入方案；试运行结果如实展示。
- **方法论**：用第一性原理（原文音译为"低性原理"，存疑）挖真需求、用 WBS 拆任务、逐个问题做 AI 提效、反复验证、最后人工兜底。他的收尾判断与全场一致：**AI 带来的只是提效，最终人要负责担责兜底**。

### 两个项目的共性骨架

| 维度 | 朱军胜 | 姜超 |
|---|---|---|
| 数据安全 | PaddleOCR 本地识别，敏感信息不出域 | 本地 OCR＋规则交叉验证 |
| 判定方式 | 规则硬编码＋AI 知识库双通道 | 规则交叉验证生成建议 |
| 人工角色 | 人工复核可推翻结论并写回 ERP | 人工兜底担责 |
| 写回企业系统 | 审核决定写回 ERP | 审核建议经 API 写回平台 |

## 常见误区

- "POC 就是把 AI 接进系统"——两个项目都把大量功夫花在规则整理、访谈洞察（手续费差值、户头表）和写回路径上，AI 只是其中一环；
- "全量数据审核靠 AI 逐张看"——两万多张发票靠的是字段硬匹配先筛、AI 复核在后；
- "限流是平台的事不用管"——每秒十次的限流直接影响批量审核耗时，是方案的一部分。

## 实验

1. 对照共性骨架表，检查你的项目四行各有还是没有，缺的写明原因；
2. 找一位业务人员做一次访谈，目标挖出一个"手册上没有"的规则（如手续费差值这类），记录下来；
3. 查清你要对接的系统有没有限流或权限约束，写进方案的限制条件一节。

## 证据

学生能讲清两个项目在"双通道判定"与"人工兜底"上的异同，并能解释为什么"票据敏感信息不出域"决定了 OCR 引擎选型。
