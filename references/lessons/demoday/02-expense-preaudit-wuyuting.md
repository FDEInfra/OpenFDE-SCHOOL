# Demo 案例：企业报销预审与财务协作（吴雨婷，常规赛道）

## 目标

学生通过这个项目看清一份高分 FDE 大作业的三块骨架：精准的问题定义、清晰的"不做什么"边界、以及可交代局限的测试设计。

## 讲授

**问题定义：财务缺的不是判断力，是时间。** 吴雨婷（字幕中也写作吴一婷/吴艺婷，为同一人）分析财务审核业务流程后得出结论：财务的核心问题不是不会判断，而是大量重复工作消耗了他们的时间——消耗主要来自员工填写错误提交，以及财务与员工反复交互的环节缺少提前分流，交互过程没有记录，后续修改容易迷失和出现偏差。

**Agent 只做三件事：**

1. 重复性劳动交给系统批量执行；
2. 输出不只是结论，还包括问题所在、制度依据、解释和操作建议；
3. 所有输出最终由人把关——明确不做自动审批和付款。

**"不做什么"和"做什么"同等重要。** 她明确列出的不做清单：不做自动审批和付款；不做自行补全和猜测；不把疑似风险直接判定为违规。她原话是"前两天作业让我明确，项目中不做什么是非常重要的"，这条边界后来成了测试集设计的重要指引。

**技术链路分五层**：飞书 BX（音译存疑）模拟企业系统数据输入 → 飞书 CLI 分页读取与鉴权 → Skill 执行规则判断 → Agent 对问题分类、解释并提出建议 → 结果本地保存 JSON，并向飞书写回批次摘要。这样设计的关键是让每一层只承担自己擅长、可测试、可追溯的职责。

**Demo 演示的四个典型场景：**

- 合规通过：AI 初审通过，五条规则全部通过，财务参考结果点击确认；
- 边界条件：设置了一个超出允许金额 **0.01 元**的案例——现实中财务可能直接放过，但它与 Skill 规则冲突，此时要求 AI 不做"差不多"的猜测，坚持提示；
- 输入错误：JSON 损坏时不让损坏数据输出为"通过"；
- 重复票号：不做判定，只提示票号重复，财务可退回并附审核意见让提交人重新核对。

降级处理的统一原则：有缺失就返回提交；超标不自行判断；重复风险只提示不判违规；输入缺失不生成"通过"，转人工复核。

**测试设计与诚实的局限声明。** 她自认在测试集部分卡了很久、与 AI 交互了很多轮，最终做了三层测试集：200 条数据证明系统能跑、读取没有问题；覆盖正常、边界、缺资端、预算错配等实际业务情况；并模拟了两条环境失败的结果。目前 14 条用例全部跑通。但她明确交代：这是模拟数据，没有真实业务专家复核，**还不能对外输出实际准确率**。

## 常见误区

- "预审 Agent 的目标是提高审批通过率"——它的目标是分流与解释，通过率是财务的事；
- "边界 case 放 AI 自由裁量更智能"——0.01 元的案例恰恰说明：规则冲突时 AI 不猜测才是可交付的行为；
- "测试跑通就能宣称准确率"——模拟数据加无专家复核，只能证明"能跑"，不能证明"跑得对"。

## 实验

1. 给你自己的大作业写一张"不做清单"，至少三条，并说明每条不做背后的业务理由；
2. 设计一个等价于"超标 0.01 元"的边界案例，写清楚你期望系统在此刻的确切行为；
3. 把你的测试集按"能跑／业务覆盖／失败注入"三层重新归类，看哪一层是空的。

## 证据

学生能复述该项目"只做三件事"和"三个不做"，并能解释为什么"不能对外宣称准确率"是加分项而不是减分项。
