# 评测驱动开发（EDD）：MVP 契约与文档留痕

## 目标

学生掌握评测驱动开发（Evaluation-Driven Development, EDD）的核心思想，会写 MVP 契约五要素，并建立「决策留痕、退役不删除」的文档纪律。

## 讲授

### 从 TDD 到 EDD

传统开发（不管敏捷还是瀑布）里，测试是流程末端的质量控制环节：聊需求、设计、分解任务、实现，最后才测试。**EDD 把评估从后置的质量保证环节变成开发的主控回路**：

1. 以最快速度做出一个 MVP——别管它垃不垃圾，你得先有一个物体才能测试，先有一个可以谈论的东西才能给别人看；
2. 之后所有的改动都围绕测出来的问题走。

讲师强调：讲这个不是为了让你「多加测试」，而是为了扭转思想——**有问题要改是极其正常的事**。接受了 EDD，你就能对客户说出：「这是个非常正常的问题，我们还在共同测试、共同设计，我需要你的帮助，你也需要我的帮助。」而不是心里发慌「是不是前期需求没设计好」。

EDD 是一套**方法论**，指导你给企业和需求方做交付，不是一门叫「EDD 服务」的生意。一个可直接引用的数字：在 EDD 下，**评估时间约占工作量的 80%**。讲师原话：「你要把百分之八十的测试时间理解成一件很正常的事情。你不要觉得是自己设计的不好，反复的再改，就是应该是这样。」

### 一个类比：公司 = 微调 + 强化学习

Kimi 创始人说过，他们公司的运行方式很像微调和强化学习的结合。微调（SFT）是「我告诉你什么是好，你照着我做」；强化学习（RL）是「我给你设定目标，告诉你做对了还是做错了，怎么适应环境你自己想」。一家好公司也一样：要有规章制度和简单培训，同时要留出空间。

这个类比可以一路映射到 EDD：用户的生产失败案例就是训练数据；先有 MVP 相当于先有预训练权重；测试要围绕一个目标，看「损失」是上升还是下降；改着改着在一个不好的地方打圈，就像训练卡在山谷里，非常正常。两个陷阱也值得记住：**测试集被当成训练集刷 benchmark**，会导致测试分数虚高、真实体验没有改善；而能承担越复杂的任务，就能得到越高质量的反馈——这就是智能体的数据飞轮，跨项目积累的「错误资产」也是你自己的飞轮。

### MVP 契约五要素

最 MVP 的阶段，只需要定义五件事：

1. AI 要干什么；
2. 干到什么程度算完成；
3. 哪些不能干；
4. 有哪些工具可以拿来干活；
5. 哪些事情一定要人类批准。

对照到电商客服案例：Agent 为电商商家回复客户消息；要解决客户最高频的 90%–95% 的问题；禁止在规则允许的范围之外做任何断言；可以使用 RAG 查询产品发货政策；规则以外的问题全部让渡给真人。这就是最简单的 MVP 契约，然后才开始造——用 Skill、用 RAG 都行。

### 文档留痕：学海瑞留卷宗

讲师 PPT 里唯一的图片是《大明王朝1566》的海瑞（逐字稿误识别为「刘恒 / Harness」，音译存疑）。海瑞到江南织造局查案，发现事情牵扯皇上，他的办法是：你讲你的，讲得好不好都没关系，**所有东西全部记录在卷宗里**，一并送朝廷。

映射到开发：不管你做的是 SQL、CLI 还是 Runtime 本身，所有的决定、决策、修复都要留文档——留了不用是一回事，想用的时候发现没留就完蛋了。具体做法：

- 让 AI 随时记录「我要干什么、我做了什么决策」，按标准软件开发的格式留档；
- 文件夹分层：开放的问题、已解决的问题（解决完不要删，挪进已解决文件夹）、不符合现状的进 archive（过期不等于没用，以后可能回头看）；
- 退役不等于删除，只是移到存档。

一个免费的最彻底的留痕：Codex、Claude Code、Trae、Qoder、WorkBuddy 等 CLI 工具，都会把你和 AI 的全部聊天记录以 JSON 或数据库形式存在本地 user 文件夹下（如 `.codex`、`.claude`）。上下文会被压缩、你会开新窗口、会换工具，但这些记录都在——你可以开一个新窗口让 AI 自己去读、去复盘你们聊过什么。文档写了读写更快，没写文档时这是兜底。

当文档足够多，结构化的系统分析才有可能发生——讲师称之为「文涌现」：没有文档，就无从涌现。

### Demo 与可交付的边界

不可能把一个东西改到无穷无尽才算完。实践中的边界是：告诉客户你的边界在哪——比如「90% 的场景可用，这两个环节需要人工干预，除此以外能跑到这个效果」，再现场跑几个具体成果，客户验收通过就是通过。哲学意义上的区分：Demo 只能在特定时间、以不保证的正确率工作；可交付的东西能在绝大多数场景或一个特定验收标准下，以最少成本稳定工作。

## 常见误区

- 「EDD 是一种可以购买的服务」——它是方法论；
- 「测试在开发序列里地位低、占比小」——EDD 下评估约占 80% 工作量，这是正常而不是失败；
- 「改完文档就可以删掉」——退役归档，不删除；
- 「聊天记录不重要」——它们是最彻底的留痕，也是评测素材（见后续课节）。

## 实验

1. 为你手头（或设想中）的一个 Agent 项目写出 MVP 契约五要素，每条一句话，对照电商客服的例子检查是否够「契约」；
2. 在项目里建 `open / resolved / archive` 三层文档结构，让 AI 把最近一周你们的关键决策补记进对应文件夹；
3. 找到你本地 `.claude` 或 `.codex` 文件夹里的历史会话记录，开一个新窗口让 AI 读其中一段并复盘「我们当时做了什么决策」，对比你自己的记忆。

## 证据

MVP 契约与三层文档结构真实存在、可检查；学生能讲清 EDD 与传统「测试后置」的区别，并说出「评估约占 80% 工作量」为什么是正常的。
