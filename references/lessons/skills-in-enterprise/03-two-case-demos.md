# 两个实战案例：文章解读 Skill 与 CLI+Skill 打通内部系统

## 目标

学生通过一生活、一企业两个完整案例，看清「输出设计决定 Skill 专业度」和「MCP 转向 CLI+Skill」的工程逻辑，并能复现其中至少一个。

## 讲授

### 案例一（偏生活）：文章解读 Skill

**先说价值。** 看文章、论文、报告不是为了看，也不是消遣，而是要对学习、科研、工作产生直接帮助。「扔进去让它帮我概括一下」帮助不大——泛泛而谈，看完没印象。

**输出设计（这是本案例的灵魂）：**

1. 一句话总结；
2. 关键要点；
3. **启发**——这是多数人想不到的：把你的岗位、研究方向、最近的困惑、读这篇文章想解决什么问题都放进去，AI 才能给最直接的启发；
4. **批判性思考**——再牛的人也有不严谨的地方：没有数据支撑直接给结论、参考资料不权威、拿幸存者偏差说事；
5. **延伸讨论**——从高度（你只能看到 60 分，AI 能给 70–80 分的视角）、深度（往深处挖）、广度（作者受篇幅限制没覆盖的）拓展。加上这一层，就已经超越文章作者本身的功力。

**输入与处理**：输入是文章/论文/报告加上你的岗位背景；处理是提取关键点 → 结合岗位给启发 → 批判性思考 → 延伸讨论。

**实测效果**：讲师用它解读一篇「智能体有自己的邮箱」的文章，AI 给出的批判与延伸包括——一天发五十封邮件工作够用吗？安全性具体怎么设计的、说清楚了吗？这是腾讯出的，其他公司能不能同样用好？发邮件前要人确认，那都在讲全自动 loop 不就卡住了？多个智能体能不能共用一个邮箱、能不能互相发邮件？这些都是原作者没考虑到的。

**关键认知**：同样是用 AI 看文章，理解不到这一层就永远做不出这个 Skill。做 FDE 也一样——你对业务的理解停留在「给我概括一下」，做出的 Skill 在专业人眼里就是个玩具。这个 Skill 讲师已开源，用的时候记得把「启发」部分的岗位换成你自己的。

### 案例二（偏企业）：CLI + Skill 打通报销系统

**背景：为什么从 MCP 转向 CLI+Skill。** 2026 年初大厂都在把各个平台改造成 MCP 挂到智能体上，后来发现上下文占用太大：一个平台可能有 100 个工具，哪怕一天都不用，也占好几千字符；装十个平台，还没开始聊上下文就占满了。于是转向 CLI 化 + Skill 挂载——Skill 渐进式加载，需要哪个功能调哪个指令。

**演示过程**：讲师模拟了一个报销平台（可登录、查列表、创建报销单，原本全要人手动操作），先用 AI 把它变成一个 CLI（带版本号，`-h` 可看支持哪些指令，可登录登出），再把网页和 CLI 放在同一目录，让 AI「根据这个 CLI 创建一个 Skill」。

**Skill 包装 CLI 的两个关键要点：**

1. **一定要让 Skill 自动安装 CLI**：把内部 Git 仓库地址，或 npm 包的 npx 安装指令写进 Skill。别人只装你的 Skill，需要操作时底层 CLI 自动下载安装。不要让用户「先打开命令行手动装 CLI 再装 Skill」——这很傻，要有用户思维、屏蔽复杂度；
2. **不要把 CLI 的所有功能都封进 Skill**：CLI 会新增功能，全封进去两者就耦合了，CLI 一变 Skill 就得跟着改。只把 `-V`、`-h`（查看全部指令）、登录、登出、查看当前用户这几个核心接口放进去。

**老系统怎么改**：一样是一步步建出来的——先把登录解决掉，再把查询解决掉，这两个打通后其他接口陆续 CLI 化，封装 Skill 时只需纳入登录、版本、`-h`、登出这几个部分。

**演示验证**：封装完成后，用自然语言「帮我查看报销系统的报销单列表」「帮我查某张报销单的信息」即可自动执行。

**本质变化**：搞端到端要打通七八个系统，如果每个都靠人切来切去组装，非常低效；全部 CLI+Skill 化之后，再往上做服务编排才能一马平川。

**Skill 不只是 CLI 的壳**：除了 CLI 功能，还可以放这个平台的业务知识（帮助 AI 更好理解这个系统），以及自然语言工作流（先干这个、后干那个的顺序约束）。讲师在大厂做的两个平台 Skill 非常复杂，光文件就有几十上百个。

**工具坐标**：Qoder 是阿里的 Coding 工具，QoderWork 偏办公；同类有字节 Trae、腾讯 CodeBuddy、OpenAI Codex。

## 常见误区

- 「看文章就是扔进去帮我概括一下」——没有岗位/困惑输入，就没有直接帮助；
- 「让用户先手动装 CLI 再装我的 Skill」——复杂度要屏蔽在 Skill 内部，自动安装；
- 「把 CLI 所有指令都封进 Skill 才完整」——会耦合，CLI 一更新 Skill 就得跟着改；
- 「Skill 只是包一层 CLI 功能」——平台知识和流程编排也该放进去。

## 实验

1. 把 lesson 02 的「输出定义+输入清单+步骤」草稿变成真实 skill.md：向 Agent 说清楚触发条件与步骤，让它生成，然后试跑 3 次，记录每次的 bad case；
2. （有命令行工具可用者）把一个常用 CLI 包装成 Skill：只放核心指令，写入自动安装方式（npx 或仓库地址），验证「只装 Skill 就能用自然语言操作」；
3. 用案例一的完整输出结构（总结+要点+启发+批判+延伸）解读一篇你专业领域的文章，和「只概括」的版本对比，写下差异。

## 证据

展示一个可运行的自创 Skill 及 3 次试跑的 bad case 记录；能讲清从 MCP 转向 CLI+Skill 的原因（100 个工具常驻占几千字符的上下文账）；能复述 CLI 包装的两条纪律（自动安装、只放核心指令）。
