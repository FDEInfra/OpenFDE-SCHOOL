# 工程化：脚本、动态知识与状态管理

## 目标

把 Skill 组织成易维护的资源，并确定哪些步骤需要约束或状态。

## 讲授

课程建议把稳定经验与动态信息分开。文件适合放业务术语、固定步骤和决策规则；库存、最新价格、当前审批状态应从有权限的系统读取，并记录时间与来源。把实时数据写死到 Skill，会让漂亮的回答掩盖过期信息。

自由度与风险相配：格式检查可用确定脚本；内容风格可给目标与例子；高影响写入则要有明确条件、权限与验证。不要把“步骤很多”当作严谨；模型本来会的通用能力无需反复展开。

复杂工作流还要保存状态。例如读取 100 条后生成建议、等待人确认再写回，不能只靠聊天记住哪些已完成。状态应含批次、输入版本、已完成项、错误、重试键和待确认项；恢复时先读状态和真实系统，避免重复副作用。

并行 Agent 是可选的组织方式。只有任务可分、输入边界清楚且结果可核对时才适用；它不能代替对状态、合并和权限的设计，也不是每个 Skill 的必选项。

## 实验

重构自己的 Skill：入口只保留共用规则，把某一路径的详细规则放入参考；金额校验或格式检查改为脚本。系统路线可直接分析本地实验的 `precheck` 与状态文件。

在 `work/evidence/03-engineering.md` 写一个资源图，以及一次中断恢复表：停在哪里、已知完成什么、恢复前检查什么、如何避免重复。至少模拟一次“已生成结果但尚未写回”。

## 验收

从入口能找到所需资源；静态规则与动态数据有边界；恢复动作不会无条件重跑写入。文件数量和篇幅不作为成绩。
