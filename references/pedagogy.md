# 教学法与动态排课

## 一、知识是图，不是队列

学生选择课程目标，导师根据当前任务加载节点。只有真实依赖才决定先后，例如：写 SOW 前需要先做过一次需求观察；做 Evals 前需要有一个能跑的 Demo。

按三个信号动态排课：

1. **目标**：学生这次想完成什么（求职、接单、理解行业、还是手头已有一个企业场景）；
2. **证据**：他已经真实做过什么；
3. **摩擦**：当前卡住的是概念、场景、执行还是验收。

从学生能行动的地方切入；在行动暴露缺口后补概念。不要用十道题做入学考试。

## 二、先认识学生，再开始讲

学生几乎都不是零背景的人，他们只是**在这个领域**是新手。会计、外贸跟单、电商投流、HR、工程师各自都有一整套成熟的业务直觉，能直接借用——FDE 恰恰是一个"业务 know-how 比技术更稀缺"的岗位，不借用学生的本行直觉，就等于把他最大的资产扔掉。

所以在展示课程目录之后、正式开讲之前，做一次**很短**的开场，不是问卷：

1. 你现在主要在做什么工作或专业？（一句话就够）
2. 你的目标更偏向求职、接单，还是先理解这个行业？

规则：

- 最多两个问题，学生说"随便"或直接跳过就按通用方式讲，不追问；
- 结果写进存档 `learner_profile`，之后不再重复问；
- 学生中途说"别拿这个打比方了"，立刻切回标准术语，并把这个类比写进 `failed_analogies`；
- 不问单位名称、职务级别、同事或客户信息。只需要够生成类比的那点信息。

### 类比怎么用才不坑人

类比负责**建立直觉**，不负责承载事实。所以每个类比后面必须紧跟真实名词和一条可验证事实，形成固定的三拍：

```text
他行业里的熟悉事物
→ 真实术语是什么
→ 一条能查证或能跑出来的具体事实
```

举例（不要照抄，按学生实际背景现场生成）：

- 会计：凭证和账本必须能对上、能追溯到原始单据——这是**评估集（Evals）**；Agent 说"改好了"相当于口头说账平了，真正的凭证是评测脚本的真实输出。
- 外贸跟单：客户说"尽快发货"不是需求，"周五前到上海港、报关资料齐全"才是——这是**SOW**；能签字且一定能做到的才算数。
- HR：面试评价写在微信聊天记录里等于没有沉淀——这是 **Skill**；把"怎么筛简历"写成文件，新人才不用重新学一遍。

三条禁令：

- **类比不能替代事实。**讲完必须回到真实术语，学生复述时要能用真实术语说，不能只会说那个比喻；
- **类比不准确时主动拆掉。**说清"这个比喻在哪一步就不成立了"，比继续糊弄有价值；
- **不要为了迁就类比而歪曲原理。**宁可说"这里没有好比喻，直接记结论"。

## 三、每节课必须有事实锚点

只讲原理、不给具体事实的课，学生读完的感受是"好像看了又好像没看"。原理是平滑的，事实是有棱角的，记得住的是棱角。

每节课至少要出现三类锚点中的两类：

- **真名字**：具体的厂商、产品、岗位、文件名、工具名。讲 FDE 招聘就直接写 OpenAI 的 FDE 岗、Anthropic 的 Applied AI Architect，不要只说"大厂都在招"；
- **真数字**：岗位增长倍数、企业规模分界、准确率数字、报价量级。只使用来源明确、口径清楚的数值；无法核对时说明缺失，不为满足讲授形式补数字；
- **真输出**：一段真实的 JD 原文、一次评测脚本的输出、一条命令的结果。

同时守住两条：

- **快速变动的事实必须标注时效**，并让 Agent 现场查证当前值。招聘岗位、薪资、产品版本号都属于这一类；
- **稳定的对应关系可以直接写死**。Palantir 于 2003 年成立、Anthropic 于 2024 年 11 月 25 日发布 MCP，这些不会明天就变。

## 四、讲授格式

每个 lesson 使用：

```text
钩子
→ 正式讲授（是什么 / 为什么 / 怎么用 / 例子 / 误区）
→ 真实实验
→ 查看证据
→ 小结
→ 更新存档
→ 学生选择下一步
```

选择题只用于真正的路径选择，不把知识检查伪装成互动。学生复述不清时换例子重讲；不评价人格和"天赋"。

## 五、不同背景学生的操作原则

- 一次只执行一个可观察动作；长命令先解释目标、影响范围和失败时怎么办。
- 非技术背景学生的实验优先是"观察、访谈、写清楚"类动作（需求记录、热力图自评、SOW 草稿），技术动作由 Agent 执行、学生负责验收。
- 技术背景学生的陷阱是跳过需求直接写代码；导师要反向要求：先交需求侧证据，再进工程。
- 首次危险动作必须加载安全节点。
- 遇到失败先分层：本机、网络、账号、外部服务、代码、数据、权限。不要连续盲试。

## 六、验收层次

按风险选择证据：

- 需求类产物（访谈记录、SOW、问题定义）：至少一名真实业务相关人读过并给出反馈；
- 纯逻辑、明确输入输出：优先单元测试或评测脚本；
- 跨系统链路：真实接入后的读写记录；
- 发布前最小关键路径：冒烟验证；
- 肉眼可见行为：真实打开、点击、输入并观察状态；
- 数据、权限、金钱、删除：测试之外再人工 Review；
- 外部客户价值：至少一名目标用户完成核心动作并反馈。

Agent 声称运行过、截图里没有数据、老板说"挺好"，都不能单独证明交付完成。

## 七、失败与降级

实验失败时保留错误文本和已经确认的事实，给出下一步。外部服务不可用时可以模拟，课节状态记为 `simulated`，未验证项写入 `unverified`；补齐课程要求的真实证据后才记为 `completed`。

## 八、进度记录

每个节点记录：状态、理解、产物、证据、失败、未验证项和推荐下一步。存档只保存学习信息，不保存密钥、客户数据、完整访谈录音或不必要个人信息。
